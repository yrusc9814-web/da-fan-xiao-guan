**文档版本：** V1.0  
**产品形态：** 响应式网页应用  
**部署环境：** Windows 本地电脑  
**使用方式：** 电脑浏览器访问；手机与电脑处于同一局域网时，通过手机浏览器访问

# 2. 产品定义

## 2.1 产品名称

暂定名称：**今天吃什么**

可在系统设置中修改名称、副标题和首页问候语。

## 2.2 产品目标

解决以下个人饮食场景：

1. 不知道今天吃什么。
2. 想按现有食材安排一顿饭。
3. 想减少连续吃同一种食物。
4. 想记录喜欢的菜谱和店铺。
5. 想优先消耗快过期或剩余食材。
6. 想记录每天吃过什么，并查看饮食统计。
7. 手机和电脑都能方便查看和维护数据。
8. 所有数据保存在自己的 Windows 电脑中，不依赖复杂云服务。

## 2.3 产品原则

- 本地优先，不强制联网。
- 操作简单，不设计复杂账号体系。
- 手机优先设计，同时保证电脑端使用效率。
- 推荐结果必须可解释、可重新推荐、可直接加入计划。
- 所有新增、编辑和删除操作都必须真正写入数据库。
- 页面刷新、浏览器关闭、电脑重启后数据不得丢失。
- Demo 中的浏览器悬浮按钮、关闭按钮等外部容器元素不属于产品界面，不复制。

# 3. 用户与权限

## 3.1 使用角色

### 管理者

默认唯一管理角色，可进行：

- 新增、编辑、删除菜谱
- 管理食材和厨房工具
- 管理店铺
- 管理食用者
- 创建和修改饮食计划
- 查看统计
- 备份和恢复数据
- 修改系统设置

### 食用者

食用者不是登录账号，只作为饮食记录中的参与人，例如：

- 自己
- 伴侣
- 家人
- 朋友

## 3.2 登录方式

V1 默认采用以下方式：

- 局域网内访问首页时输入一个简单访问 PIN。
- PIN 可在设置中关闭。
- 不建设注册、短信、邮箱和多角色权限系统。
- 登录状态默认保留 30 天。
- 修改、删除和恢复数据时仍需二次确认。

# 5. 页面与功能需求

# 5.1 首页

## 5.1.1 页面目标

快速回答“今天吃什么”，并查看当天餐次安排。

## 5.1.2 页面结构

从上至下：

1. 页面标题区
2. 全局搜索框
3. 六个快捷功能卡
4. 日期横向选择器
5. 当日计划卡
6. 推荐结果或近期内容

## 5.1.3 标题区

显示：

- `Chapter 01`
- 主标题：`今天吃什么？`
- 副标题：`让今天的美味，交给一点点幸运吧`

电脑端可将 Chapter 弱化，不作为主要信息。

## 5.1.4 全局搜索

搜索范围：

- 菜谱名称
- 菜谱食材
- 菜谱标签
- 店铺名称
- 菜系
- 菜品
- 店铺标签
- 饮食日记备注

搜索结果按类别分组显示：

- 菜谱
- 店铺
- 日记

搜索支持：

- 模糊匹配
- 最近搜索
- 清空输入
- 无结果状态
- 点击结果进入详情页

## 5.1.5 六个快捷入口

### A. 帮我决定

进入随机推荐页。

### B. 搭配一顿饭

根据已选餐次和条件生成一组餐食组合。

默认组合结构：

- 主菜
- 配菜
- 主食
- 汤品或饮品，可选

规则：

- 不强制每次生成四项。
- 根据菜谱的标签和餐次匹配。
- 避免同时出现多个相同主食或相同烹饪类型。
- 用户可锁定其中某一项，只重新生成其他项。
- 结果可一键加入当天计划。

### C. 消灭库存

进入剩菜消灭计划。

### D. 收藏推荐

展示用户收藏过的菜谱和店铺，并支持再次随机抽取。

### E. 最近推荐

展示最近的推荐历史。

每条记录包含：

- 推荐时间
- 推荐对象
- 使用条件
- 是否接受
- 是否加入计划
- 是否重新推荐

### F. 今日计划

滚动或跳转到当日计划区域。

## 5.1.6 日期选择

显示：

- 今天
- 明天
- 后续日期

移动端：

- 横向滑动日期卡片。
- 默认展示未来 7 天。
- 点击后刷新计划。

电脑端：

- 展示完整一周。
- 支持上一周、下一周。
- 支持打开日期选择器。

## 5.1.7 当日计划

默认餐次：

- 早餐
- 午餐
- 晚餐
- 下午茶
- 汤品

每个餐次显示：

- 当前安排
- 获取方式：自己做、到店、外卖
- 菜谱或店铺名称
- 食用者
- 完成状态
- 快捷编辑

空状态显示“暂无”。

点击某一餐次可：

- 手动选择菜谱
- 手动选择店铺
- 调用帮我决定
- 调用搭配一顿饭
- 清空计划

## 5.1.8 计划状态

状态包括：

- 未安排
- 已安排
- 已完成
- 已取消

确认完成后：

- 自动生成一条饮食日记草稿。
- 自动扣减有关库存。
- 用户确认后写入正式日记。
- 不自动扣减时可在设置中关闭。

# 5.2 帮我决定

## 5.2.1 页面目标

根据菜谱、店铺、库存和用户条件随机推荐一个合适结果。

## 5.2.2 推荐模式

### 直接推荐

不展开筛选条件，使用系统默认条件进行推荐。

### 根据筛选条件

用户选择条件后进行推荐。

两个模式在视觉上采用切换按钮，不同时高亮。

## 5.2.3 主决策区

沿用 Demo 的圆形决策器：

- 顶部箭头
- 中央餐具图标
- 文案：`点击决定`
- 显示符合条件的候选数量
- 主按钮：`帮我决定`

优化要求：

- 圆形只作为视觉表达，不做复杂转盘动画。
- 点击后采用 500–900ms 的轻量随机切换动画。
- 禁止持续旋转或长动画。
- 候选数量为 0 时，按钮禁用并提示用户放宽条件。

## 5.2.4 筛选条件

### 餐次，可多选

- 早餐
- 午餐
- 晚餐
- 下午茶
- 汤品

### 获取方式，可多选

- 自己做
- 外出觅食
- 外卖

### 标签，可多选

默认标签：

- 辣
- 减脂
- 快手菜
- 一人食
- 清淡
- 下饭
- 素食
- 肉类
- 海鲜
- 主食

用户可在设置中增加自定义标签。

### 最近多久不能重复

- 不限
- 3 天
- 5 天
- 1 周
- 1 个月
- 3 个月

### 不想吃

文本输入，逗号分隔。

匹配对象：

- 菜名
- 菜谱食材
- 标签
- 店铺类型
- 菜系

### 想吃

文本输入，逗号分隔。

### 随机程度

- 普通
- 完全随机
- 尝鲜

定义：

- **普通：** 优先推荐高评分、常收藏和近期未吃的内容。
- **完全随机：** 在符合硬条件的候选中均匀随机。
- **尝鲜：** 优先推荐从未吃过或低频内容。

## 5.2.5 推荐结果

推荐完成后显示结果卡：

- 图片
- 名称
- 类型：菜谱、到店、外卖
- 匹配原因
- 使用到的库存食材
- 最近食用时间
- 评分
- 标签

操作：

- 加入今日计划
- 换一个
- 收藏
- 查看详情
- 标记不想吃
- 调整条件

## 5.2.6 推荐规则

推荐候选池来源：

- 我的菜谱
- 收藏店铺
- 可选库存菜谱
- 可选历史推荐

硬过滤：

- 餐次
- 获取方式
- 不想吃
- 重复周期
- 必须消耗库存
- 食用者忌口

软排序：

- 想吃关键词
- 收藏
- 评分
- 库存匹配度
- 快过期食材
- 最近未推荐
- 尝鲜程度

每次推荐必须保存推荐历史。

定义：

- **允许购买：** 可缺少少量食材，并列出采购清单。
- **必须消耗：** 用户选择需要优先消耗的食材，推荐结果必须包含这些食材。

# 7. 响应式设计

## 7.1 断点

- 手机：`0–767px`
- 平板和小窗口：`768–1199px`
- 电脑：`1200px 及以上`

## 7.2 手机端

- 底部四栏导航固定。
- 内容单列。
- 页面左右边距 16px。
- 卡片间距 12–16px。
- 主要按钮高度 48–52px。
- 底部固定按钮需要避开系统安全区。
- 表单输入框不得小于 44px 高。
- 横向日期列表允许滑动。
- 不使用依赖鼠标悬停的交互。

## 7.3 平板端

- 仍保留底部导航或切换为窄侧栏。
- 首页快捷入口保持三列。
- 统计卡片允许两列。

## 7.4 电脑端

采用左侧导航 + 主内容区：

### 左侧导航

宽度建议 220px：

- 产品名称
- 首页
- 厨师
- 觅食
- 日记
- 设置

### 主内容区

最大宽度 1440px，居中显示。

布局：

- 首页快捷入口：3–6 列，根据宽度变化。
- 日期和当日计划：可左右分栏。
- 厨房食材和工具：双列。
- 觅食店铺：卡片网格。
- 日记：左侧日历，右侧记录。
- 统计图表：两列。

### 电脑端特殊要求

- 不把手机页面简单拉宽。
- 不保留底部导航。
- 不让正文无限扩展。
- 表单不全屏覆盖。
- 鼠标悬停仅做轻微反馈，不作为唯一操作方式。

## 12.3 启动方式

用户双击：

```text
start.bat
```

服务启动后：

- 电脑访问：`http://127.0.0.1:8787`
- 手机访问：`http://电脑局域网IP:8787`

启动脚本需要：

1. 检查端口是否被占用。
2. 检查数据库是否存在。
3. 首次启动自动初始化数据库。
4. 启动成功后自动打开电脑浏览器。
5. 在命令窗口显示手机访问地址。
6. 写入运行日志。

## 12.4 手机访问条件

- 手机和电脑连接同一个 Wi-Fi。
- Windows 电脑保持开机。
- 后端监听局域网地址。
- Windows 防火墙允许该端口访问。
- 手机浏览器输入电脑局域网 IP 和端口。

系统设置页显示：

- 当前电脑访问地址
- 当前手机访问地址
- 二维码
- 服务状态
- 数据库状态

## 12.5 自动启动

可选项：

- 设置为 Windows 登录后自动启动。
- 使用 Windows 任务计划程序。
- 默认不强制启用。

## 12.6 数据备份

自动备份规则：

- 每天首次启动后备份一次。
- 数据库写入备份目录。
- 默认保留最近 30 份。
- 图片目录不每天完整复制，采用增量或打包备份。
- 手动备份时生成一个 ZIP 包，包含数据库、图片和配置。

恢复要求：

- 恢复前自动再备份当前数据。
- 恢复过程中禁止写入。
- 恢复失败时自动回滚。

- 列表筛选响应低于 500ms。
- 保存操作低于 1 秒。
- 推荐计算低于 1 秒。

## 13.2 数据安全

- 所有写入使用数据库事务。
- 数据库定期备份。
- PIN 只保存哈希。
- API 默认只允许局域网访问。
- 不把敏感配置写入前端代码。
- 上传文件名由后端重新生成。
- 防止路径穿越。
- SQL 查询全部参数化。

## 13.3 稳定性

- 后端异常不得导致数据库损坏。
- 前端请求失败后可重试。
- 保存表单失败时保留用户输入。
- 应用启动时检查数据库完整性。
- 日志按天滚动。
- 日志默认保留 14 天。

## 13.4 兼容性

电脑端：

- Windows 10、Windows 11
- Chrome
- Edge

手机端：

- iPhone Safari
- Android Chrome

最低宽度：

- 360px

# 14. 优化项说明

以下为基于 Demo 的直接优化，已纳入正式需求：

1. **桌面端不再照搬手机底部导航**
   - 改为左侧导航和多列布局。

2. **推荐结果增加解释**
   - 显示为什么推荐、使用了哪些条件、有哪些库存匹配。

3. **推荐结果直接形成闭环**
   - 可加入计划、收藏、换一个、记录不想吃。

4. **库存增加数量和到期时间**
   - Demo 只展示食材入口，实际使用必须支持库存数量和保质期。

5. **已完成计划自动生成日记草稿**
   - 避免计划和日记完全割裂。

6. **食用者忌口进入推荐逻辑**
   - 让食用者管理不只是独立资料页。

7. **删除采用软删除**
   - 防止历史统计被破坏。

8. **图片存本地文件，不塞入数据库**
   - 降低 SQLite 体积和损坏风险。

9. **AI 标签为可选能力**
   - 不配置 AI 也能正常使用。

10. **空状态减少无意义大留白**
    - 保留 Demo 的可爱感，但提高信息密度。

11. **推荐转盘采用轻动画**
    - 保留视觉记忆点，不做复杂高成本动画。

12. **增加备份、恢复和局域网访问说明**
    - 这是 Windows 本地自用应用必须具备的能力。

# 16. 验收标准

## 16.1 功能验收

1. 新增菜谱后，刷新页面和重启电脑后仍存在。
2. 新增店铺后，可分别在到店和外卖列表中正确显示。
3. 新增食材后，可被库存推荐和剩菜消灭计划读取。
4. 帮我决定必须根据筛选条件过滤候选。
5. 最近多久不能重复必须真实影响推荐结果。
6. 推荐结果可一键加入指定日期和餐次。
7. 完成计划后可生成饮食记录草稿。
8. 饮食记录可按日期、来源、餐次和评分筛选。
9. 月度统计必须基于真实数据库记录计算。
10. 删除食用者不得破坏历史记录。
11. 电脑浏览器和手机浏览器访问同一份数据。
12. Windows 重启后数据仍完整。
13. 手动备份后可恢复到备份时状态。
14. 图片刷新和重启后仍能正常显示。

## 16.2 视觉验收

1. 色系符合浅粉、白色卡片、柔和辅助色。
2. 手机端保持 Demo 的四栏底部导航。
3. 电脑端使用侧边导航，不拉伸手机布局。
4. 卡片圆角、阴影、按钮和输入框保持统一。
5. 页面无横向溢出。
6. 360px 宽度下按钮和文字不重叠。
7. 所有表单在手机键盘弹出后仍可操作。
8. 底部按钮不被手机安全区遮挡。
9. 弹窗、抽屉和加载状态具有统一动效。
10. 空状态保留插画感，但不出现过度空白。

## 16.3 技术验收

1. 只使用一个 SQLite 主数据库。
2. 数据库写入采用事务。
3. 图片保存在本地目录，数据库保存相对路径。
4. API 错误有统一错误码和错误信息。
5. 服务只允许配置的局域网范围访问。
6. PIN 不以明文存储。
7. 备份文件可校验并成功恢复。
8. 日志中不得记录 PIN、Token 或完整敏感配置。
9. 前端构建产物由后端统一提供。
10. 无需 Docker、PostgreSQL 或外部云数据库。
